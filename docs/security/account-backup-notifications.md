# Account cleanup, database backup, and notification preferences

Account deletion now runs explicit private-resume cleanup before deleting the user. Stored paths must belong to `resumes/{user_id}/`. Missing files are accepted so a retry can finish after partial cleanup. Storage failures stop account deletion and leave resume/owner rows available for retry. The owner row is locked during cleanup/deletion. Storage and SQL cannot share a rollback: if later cleanup or SQL fails, files already removed remain removed, while their rows remain until a retry. Existing orphan files from earlier deletions require a separate reviewed cleanup; this change does not scan or delete them.

Database backups use an argument array rather than shell interpolation/redirection. Credentials come from runtime configuration and are passed to the child environment, not command arguments or logs. `mysqldump` must finish successfully within five minutes, produce SQL schema, and end with its completion marker. Failed/partial output is removed. There is no simulated fallback. Successful files have mode 0600, random temporary names, and are removed after download. Non-MySQL connections fail explicitly. The dump includes routines, triggers, and events; the configured database user needs the corresponding permissions. `--single-transaction` assumes transactional tables and no concurrent DDL for consistent backups. Runtime TLS/client configuration remains an infrastructure responsibility.

Exit/structure checks detect common failures; they do not prove restorability. Before enabling this operationally, restore a generated backup into a disposable, isolated MySQL instance of the target version, verify schema/indexes/constraints/triggers/routines/events and representative row counts, then record the outcome. No real database dump or restore was run during this fix. Automated tests use synthetic process output, disposable SQLite tables, fake storage, and fake mail.

`User::wantsEmailNotification()` combines feature entitlement, the master email switch, and the selected type preference. Scheduled interview emails, interview reminders (command and model entry point), and goal achievement emails use it. Authentication and transactional account emails are outside this optional-notification policy. The manual `email:test` development command remains an explicit diagnostic send rather than a scheduled notification.
