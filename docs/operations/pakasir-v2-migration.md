# Pakasir API v2 migration

Implemented locally on 20 October 2026. Production and the Pakasir dashboard have not been changed.

## Changes

- Hosted checkout first calls `POST /api/v2/create-transaction/{slug}/{order_id}` with `method=payment_link` and the stored amount. Credentials travel only in `X-Api-Key`; redirects from authenticated API requests are not followed.
- The returned `txn_id` is stored in the new nullable, unique `payments.pakasir_txn_id` column. `pakasir_is_sandbox` records the expected project environment. The returned payment link must belong to the same transaction on `https://app.pakasir.com/pay-v2/`.
- Existing QRIS and bank-transfer choices remain. QRIS appends `qris_only=1`; the return URL preserves the generated order identifier. Unsupported legacy bank codes are no longer accepted as checkout choices.
- Browser returns, status polling, webhook verification and `payments:sync-pending` use `GET /api/v2/transaction-status/{slug}/{txn_id}`. A shared cache and lock reuse a provider response for four seconds, including failures. Cached results are still validated against the expected order, amount, transaction and environment.
- Webhooks require the configured `X-Secret` before parsing or looking up an order. Empty server configuration fails closed. V2 payloads do not need a `project` property. JSON sent without an application/json content type is supported because the official example uses that form.
- Both webhook identity and independent provider verification must match the stored order. Sandbox/live mismatches, unknown statuses, malformed responses and missing transaction IDs cannot grant credits or premium.
- A completed webhook whose provider lookup is still pending receives 503, requesting retry rather than acknowledging a potentially stale cached confirmation. The normal sync command remains a reconciliation path.
- Settlement retains the row lock and unique grant ledger. Repeated webhook, browser return, polling and sync cannot regrant a payment or downgrade success. Verified v2 cancellation is reflected locally.
- The service also supports v2 cancellation and sandbox-only simulation. Authenticated write requests have a local two-per-second throttle per project/operation. No live payments, simulations or cancellation calls were made during implementation.
- Provider errors and credentials are not exposed in checkout responses. Payment links resumed from history must use the stored v2 identity and trusted provider host.

## Production settings

Set these on the production server, retaining the existing correct project slug and API key:

```dotenv
APP_URL=https://trakerja.com
PAKASIR_SLUG=your-existing-project-slug
PAKASIR_API_KEY=your-existing-project-api-key
PAKASIR_WEBHOOK_SECRET=the-secret-from-the-project-details
PAKASIR_SANDBOX=false
```

`PAKASIR_WEBHOOK_SECRET` is the webhook secret in the Pakasir project's detail page, not the API key. Do not copy the example credentials from Pakasir's documentation. A sandbox project uses `PAKASIR_SANDBOX=true` and should be tested against a separate test environment/database.

In the existing Pakasir project's settings, set the webhook URL to:

```text
https://trakerja.com/payment/webhook
```

The browser return URL is generated by the application; do not configure the webhook URL as the browser return.

Deploy the code with checkout paused, then run from the deployed Laravel root:

```sh
php artisan migrate --force
php artisan config:cache
php artisan queue:restart
```

The production cache must be shared between PHP requests/workers and support locks (for example the application's database or Redis cache). An in-memory per-process array store is only for tests; it cannot coordinate provider rate limits across workers.

## Existing transactions

The migration adds nullable identity fields without changing amounts, statuses, entitlements or old records. Previously settled payments keep their membership and history.

Pending v1 orders do not have the required v2 `txn_id`. They are not silently recreated, rebound to a webhook-supplied ID or automatically marked paid. Their detail page directs the owner to support and does not offer the retired payment link or repeatedly poll v1. Reconcile any potentially paid v1 order against the provider's records before resolving it or requesting another payment. No bulk conversion or automatic legacy settlement is included.

## Verification

All provider requests in automated tests are faked with stray network requests blocked. Coverage includes checkout headers/body and identity persistence, malformed/malicious provider links, failures/timeouts, four-second cache refresh and cached-order binding, webhook secret/environment/order/amount validation, raw JSON webhook parsing, stale-pending webhook retry, cancellation, browser-return/webhook reuse, historical records, account isolation, premium renewals, rollback and the existing grant ledger.

83 PHP tests / 477 assertions and 25 payment JavaScript tests passed before the documentation-only wrap-up. The migration test also starts with a historical paid order before adding the v2 columns and verifies that its status, amount, paid timestamp and receipt remain intact without inventing a provider identity. PHP syntax checks and `git diff --check` passed. No production data, credentials or dashboard settings were changed. A real provider sandbox round trip remains a deployment verification step after the actual secret/project environment is configured.

### Delivery gate for the legacy-order message

- Hard gate PASS: the existing payment layout is reused; rendered feature tests verify the real support link and absence of inactive polling/resume controls for legacy orders. No invented claims, assets or provider states were introduced. Language files parse through the rendered tests.
- Purpose gate PASS: no new visual techniques, animation or decoration; the new message explains a concrete migration constraint rather than exposing API internals to a customer.
- Liveliness PASS: existing workspace typography, status hierarchy, theme styles and motion settings are retained; the actionable support link replaces an unusable retired checkout.
- Craft PASS: paid legacy receipts and normal v2 waiting pages remain covered separately, including ownership checks, truthful grants and terminal status handling. New English and Indonesian text fits the existing explanatory paragraph; no new layout component or inert control was added.
